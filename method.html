Method and sources

A local SQLite shop supplied repeatable orders, receipts and account roles. This page specifies the fixture, the browser journey, what counted as evidence, and how to repeat it.

Testbed and scope

The course brief calls Topic 11 “Comparison of the Most Used Penetration Testing Tools and Systems.” The practical question here is how three HTTP proxies support evidence gathering on one local shop. The chosen tools cover desktop inspection, passive rule-based triage and saved-flow analysis. The study measures this selection and makes no popularity estimate.

Stillroom uses Node.js 26.13.1 and SQLite. Nine products, two customers with separate order histories, and a staff account form the starting state. Checkout uses simulated payment. Staff can advance fulfilment and customers can see their own status. Each proxy run started the same server code with a fresh in-memory SQLite database at 127.0.0.1:18770. The ordinary shop uses a persistent database at port 8770.

Artix Linux, Chromium 156.0.8078.4, a clean browser context per proxy, ordinary HTML form submissions and plain loopback HTTP were common to all three journeys. The test runner drove the same UI actions. Media was captured on 19 November 2026 UTC. Burp used a temporary Community project with interception off, ZAP used Safe mode with the packaged release passive rules (revision 70), and mitmdump saved the proxied exchanges for offline reading.

Repeat the normal browser journey

  1. With Node 24 or later, run node fixture.mjs in the showcase source directory. Open http://127.0.0.1:18770/ through one proxy in a fresh browser profile. Keep the target and listener on loopback. Use the test accounts in the shop README.
  2. Browse page two, select Coffee, sort by ascending price and search for Roaster's. Apply the harmless marker from the reflected-text case and read the rendered result.
  3. Sign in as Alex, add Roaster’s Reserve, change the cart quantity to two and approve the test payment. Open the order and download the receipt.
  4. Sign out and sign in as Sam. Open the same order from Fulfilment and choose Start processing. Sign in again as Alex and read the updated order and timeline. Finish with Jamie’s My orders view.
  5. Match the exchanges in the tool history or saved flow. For ZAP, wait for its passive queue to empty. Stop the fixture with Ctrl+C and start it again before repeating with another tool.
  6. From the shop directory run npm run check and node --test. Compare the full suite output with the focused commands on the four case pages. Timing uses a separate public GET with the three listeners running and an idle recorder.

How the records were compared

Browser response events were collected once per tool through checkout, receipt, staff change and the customer reads. Native evidence came from Burp’s Save items export, the ZAP messages and alerts API, and a saved mitmdump flow file read offline. Method, decoded route and query, status and sequence agreed for every one of the 40 application documents. The retained extracts omit cookies, login bodies, unrelated traffic and proxy credentials.

For the performance comparison, curl 8.23.0 timed a single HTTP connection and complete document response per sample. Two blocks produced 64 measurements per path, with a cyclic path order so that each path occupied each position equally often. The median is the middle pair’s mean. The p95 uses the nearest rank. Absolute latency, the rules installed in ZAP and the hardware affect comparisons with another machine.

Retest from the delivered source

The recorded app passed its syntax checks and all 12 tests. A second run extracted the clean source archive in another directory, verified all nine source and test file hashes, reran the syntax check and passed the same 12 tests on fresh SQLite fixtures. State of the art in web application testing with HTTP proxies

One browser action can trigger both a page request and a later API call. OWASP’s Web Security Testing Guide recommends recording the method, URL, parameter locations and authentication state when mapping application entry points. Each request and its response give the three tools a common unit for comparison. Coverage depends on which exchanges pass through the proxy. [1]

Manual inspection with Burp Suite Community Edition

Community Edition includes Burp Proxy and its numbered HTTP history. With Intercept off, the history continues to record traffic. If the response to a sign-in POST sets a session cookie and redirects the browser, a reviewer can cite the entry showing the POST, redirect status and Set-Cookie header. PortSwigger lists its automated web vulnerability scanner as a Professional feature. [2] [3]

Passive checks with ZAP in Safe mode

ZAP’s passive scanner applies rules in the background to HTTP and WebSocket messages already passing through the proxy. Safe mode blocks active scanning, crawling and resending requests. [4] [5]

For example, rule 10010 flags a cookie issued without HttpOnly. A reviewer can inspect the Set-Cookie header and check which cookie the alert names. If it carries the session identifier, HttpOnly would prevent page scripts from reading that value. [6] [7]

Offline review with mitmproxy and mitmdump

mitmproxy provides an interactive terminal view of HTTP exchanges. Its non-interactive companion mitmdump can save those exchanges to a flow file and filter it offline. A second reviewer can apply the same POST filter to the same capture and examine the sign-in response without repeating the login. [8]

Why an alert needs a second observation

ZAP describes rule 10031 as a passive lead for analyst review. For a reflected value, the HTML context determines which characters must be encoded. In the catalogue case, the raw response and the browser’s parsed document answer different questions. For SQL construction, the application’s prepared statement and separately bound values supply evidence an HTTP proxy cannot see. [9] [10] [11]
